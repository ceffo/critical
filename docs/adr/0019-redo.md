# ADR 0019: Redo replays the newest popped transaction

**Status**: accepted, 2026-10-15. Amends [ADR 0007](0007-hp-ledger.md) step 2 (what "voided"
means), [ADR 0010](0010-action-stack-and-undo.md) Consequences and
[ADR 0018](0018-transactions-and-undo.md) step 6 and Consequences (redo is no longer "later").

## Context

[ADR 0018](0018-transactions-and-undo.md) makes every gameplay mutation one transaction, which
the journal's Undo pops whole. Its step 6 keeps every popped transaction on the log with its
entries, payloads and both snapshots so that a later rule can replay it. User, 2026-10-15:
*"eventually support redo by replaying popped transaction"*; the redo lands before Saturday.

The scoper's design defaults (supervisor, the same day) are the steps below. Two things in the
code shaped them:

- A void was the last word on an entry: the storage allowed one void per entry and every query
  treated "has a void" as popped. A redo has to be undone again, so an entry can now be popped,
  replayed and popped again, each time with a new correction row.
- Snapshots were only ever written back as "before". Two "afters" turned out not to be enough to
  write the state back on their own: the initiative's "after" is encoded before its entry has an
  id (the reroll guard, ADR 0018 step 5, reads that id), and the "after" of an item use that
  spent the last charge says "removed", which the items restorer ignored.

## Decision

Paths are under `api/internal/` unless they start with `web/`.

1. **Replay un-pops the transaction's entries.** A redo writes the "after" of every snapshot of
   every popped entry of the transaction back through the same restorer the undo used, oldest
   entry first (the reverse of the pop, so a state two entries snapshot ends at the newest
   "after"), and records a `redo` correction on each entry. Nothing is deleted or rewritten: the
   log stays append-only, and an entry is popped exactly when its newest `void` or `redo`
   correction is a `void` (`actionlog.Entry.Voided`; every storage query that skips popped
   entries, the HP total and a correction step's amend follow the same rule). Nothing is rerolled
   or recomputed: the entries come back with their payloads and HP deltas as recorded, so HP gets
   the recorded applied delta back (the pop order guarantees the state the cap and floor were
   computed against). A restorer whose "after" cannot name the entry that recorded it implements
   `actionlog.Replayer` and gets the replayed entry's id (the initiative); every restorer writes
   its own "after" faithfully (an item a state marks removed is deleted). Migration 026 lets the
   kind be `redo` and drops the one-void-per-entry index; existing rows keep their ids.
   Tests: `domain/service/actionlogsvc` `TestRedo_ReplaysTheNewestPoppedTransaction` ("oldest
   first, the after written back"), `TestEntry_NewestVoidOrRedoDecides`; `adapters/actionlogdal`
   `TestRedo_NewestVoidOrRedoDecidesInStorage`, `TestListActiveEntries_SkipsThePoppedEntries`,
   `TestLatestActiveID_NewestEntryNotPopped`; `domain/actionlog`
   `TestStandingVoids_NewestVoidOrRedoDecides` (the one rule the adapter applies to every popped
   lookup); `domain/service/buffsvc` `TestInitiativeRestorer`
   ("replay names the replayed entry"); SQLite migration 026 did the same
   on the rows of its time (a past migration; the per-migration test was deleted with the squash into the PostgreSQL baseline, [ADR 0025](0025-postgresql-storage.md) step 2.3); the redo writes each
   snapshot's "after" back through the same restorers the undo uses, which the root registers
   (`composition` `TestUndo_EveryStateKeyIsRestoredThroughItsServicesStorage`).
2. **The redo stack.** The transaction a redo replays is the one popped last and not redone since,
   as long as it is above the live top (the newest non-popped entry, ADR 0010 step 1); otherwise
   there is nothing to redo. That makes the redo stack the run of popped transactions above the
   live top, the last popped first, and any new transaction empties it: a transaction pushed after
   a pop is either live (the popped one is then below the live top) or popped later (it is then
   the one popped last). Undo after a redo pops it again; redo after redo replays the next one.
   `GET /api/log` names the target as `redo`, the transaction's first entry shaped as a log entry
   (null when there is nothing to redo), so the tooltip names it even when it is not among the
   listed entries. A request that writes no entry, and a note amend, leave the redo stack alone.
   Tests: `domain/service/actionlogsvc` `TestRedo_ReplaysTheNewestPoppedTransaction` ("a newer
   transaction is live: nothing to redo"); `domain/actionlog` `TestLatestPopped_NewestStandingVoid`;
   `adapters/actionlogdal` `TestLatestPopped_EntryOfTheNewestStandingVoid`; `rest/router`
   `TestLogRedo_WireShape`.
3. **Redo is guarded like undo.** `POST /api/log/redo` with `expectedRedoId`, the `redo` id the
   client read. Reading the target, the check, every replay and every redo correction run in one
   DB transaction: a stale target is refused (409, `log_redo_changed`) and nothing changes, no
   target is refused (409, `nothing_to_redo`), and a restorer failing mid-replay leaves no redo
   and no partial state. The redo answers with the transaction's first entry, live again. In the
   journal header, a Redo button ("Rétablir" in French) sits next to Undo, with Ctrl/Cmd+Shift+Z
   (outside text fields and open overlays); its tooltip names the transaction, and it is disabled
   ("Nothing to redo" / "Rien à rétablir") when there is none.
   Tests: `domain/service/actionlogsvc` `TestRedo_ReplaysTheNewestPoppedTransaction` ("stale expected
   redo changes nothing", "restorer fails mid-replay: no partial state");
   `composition` `TestPostgresStorage_EveryAdapterRunsOnTheCallersTransaction` (every adapter writes in
   the transaction the redo runs in; the rollback itself is the database's,
   [ADR 0025](0025-postgresql-storage.md) step 7); `rest/router` `TestSpecialSentinels` ("redo stale target", "nothing to redo");
   `web/src/lib/undoButton.test.ts` `redoButtonState` (en/fr); `web/src/lib/undoShortcut.test.ts`
   `isRedoShortcut`; `web/src/stores/undo.test.ts` ("journal Redo replays the popped transactions
   in order", "journal Redo with a stale target"); `web/e2e/cast.spec.ts` "cast, heal, cast: the
   journal Undo pops the cast on top, then the heal" (extended: Redo replays the heal, then
   Ctrl+Shift+Z the cast; slots and HP back).

## Consequences

- An entry's corrections can read void, redo, void…; the journal reads the status (popped or
  not), never the correction kinds. "Undone" / "Annulé" shows while the entry is popped.
- A correction step (ADR 0010 step 6) that is redone puts its amend back in effect: the corrected
  roll reads its corrected payload again.
- The redo stack lives in the log, not in a client: every client sees the same target, and it
  survives a reload.
- Not covered: redoing a transaction once something newer was pushed (it stays popped on the log,
  as before), multi-transaction redo.
